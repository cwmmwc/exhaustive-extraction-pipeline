# Experiment Log: Exhaustive Extraction Pipeline

**Project:** AI-assisted extraction of structured data from Native American land dispossession archives  
**PI:** Christian McMillen, Department of History, University of Virginia  
**Period:** March 16 – April 14, 2026  
**Purpose:** This log documents the full iteration history — including failures, wrong assumptions, and dead ends — to support a forthcoming presentation and paper on the use of large language models in historical research.

---

## Why Document the Failures?

Anyone can report "we used AI and it worked." The value for digital humanities researchers is in understanding where it didn't work, why our assumptions were wrong, and what we changed. Every major improvement in this pipeline came from a failure that forced us to rethink something we took for granted.

---

## Phase 1: Entity Deduplication (March 16–23)

**Goal:** Deduplicate extracted entities across documents using fuzzy string matching.

Built a two-phase pipeline: Phase 1 clustered exact and near-exact matches across the Crow corpus; Phase 2 added fuzzy matching with a human review workflow. Three dedup runs on the Crow corpus, then expanded to the Kiowa/KCA corpus after v3 re-extraction (256 documents, March 19).

**What worked:** The fuzzy matching correctly identified entity variants (e.g., "John Collier" / "Commissioner Collier" / "Collier, John"). The human review step caught false positives the automated matcher missed.

**What we'd do differently:** The entity deduplication pipeline was built before we had a stable extraction schema. Some of the entity variants it resolved were artifacts of inconsistent extraction, not genuine name variation. In hindsight, improving extraction consistency would have reduced the dedup problem.

## Phase 2: The Fine-Tuning Experiment (March 23–24)

**Goal:** Fine-tune Llama 3.3 70B on Claude's extractions to get Claude-quality output at open-source cost.

**The hypothesis:** If we showed Llama enough examples of "correct" extractions (generated by Claude Sonnet), it would learn the extraction format and approach Claude's quality.

**What happened:** Fine-tuning made the model *worse*.

| Model | Items Extracted | % of Claude |
|-------|----------------|-------------|
| Claude Sonnet (baseline) | 321 | 100% |
| Llama 3.3 70B (untuned) | 148 | 46% |
| Llama 3.3 70B (fine-tuned) | 122 | 38% |

The fine-tuned model extracted fewer items than the untuned base on 2 of 3 test documents.

**Why it failed:**
1. **Training data poisoned the model with sparsity.** 59% of training examples had empty v4 fields (correspondence, fee_patents, legislative_actions), because those categories simply didn't apply to most chunks. The model learned that "correct output = sparse extraction." It got better at producing valid JSON and worse at finding things.
2. **The richest examples were truncated.** Together AI's 24K token sequence limit cut off 10 of our best training examples (9.17%) — exactly the ones that demonstrated dense extraction.
3. **The gap isn't format, it's comprehension.** We assumed the problem was teaching Llama the output format. The actual problem is that Llama doesn't read historical documents as carefully as Claude. No amount of format training fixes that.
4. **The cost math killed it anyway.** Fine-tuned models on Together AI require dedicated endpoints at $0.532/min ($31.92/hr). At that price, Claude is cheaper per document. Total cost of the experiment: ~$71 for nothing.

**Lesson:** Fine-tuning a weaker model on a stronger model's outputs teaches it to mimic the format, not the reasoning. The "intelligence" is in how carefully the model reads the source text, and that can't be transferred through supervised fine-tuning on 109 examples.

## Phase 3: Open-Source Model Benchmarking (March 23–26)

**Goal:** Find an open-source model that could replace Claude Sonnet for extraction, reducing per-document cost from ~$3–5 to near zero on university HPC.

**Test corpus:** 3 Crow documents (IDs 695, 798, 811), ~100K characters total.

### Models tested and results:

**Llama 4 Scout:** Complete failure. Zero usable output on all three documents. The model could not produce structured JSON extraction at all.

**Llama 4 Maverick:** 25% of Claude. Worse, it hallucinated — fabricating names and events not in the source documents. For historical research, hallucination is worse than missing data. A gap in coverage can be identified; a fabricated "fact" might not be.

**Llama 3.3 70B (untuned):** 46% of Claude. Consistent underperformance across all document types, but at least the output was real.

**Few-shot prompting:** No measurable effect on any Llama variant. We tried providing 1–3 example extractions in the prompt. The models produced the same output with and without examples.

**Qwen 2.5 72B (March 26, UVA HPC, 2x A100 80GB):** Catastrophic failure. All 3 documents produced invalid JSON. Response times were suspiciously fast (0.2–1.2 seconds for documents that should take minutes), suggesting the model wasn't actually processing the input. When it did produce valid output: 114 items total, zero fee patents (vs. Claude's 169, Kimi's 268). After multiple attempts adjusting max_model_len and GPU memory, Qwen was abandoned.

**Kimi K2.5 (March 25):** The breakout result. 73% of Claude overall — but with a critical surprise.

### The fee patent discovery

On the CCF 56074 benchmark (a 221-page Board of Indian Commissioners report dense with allotment records):

| Model | Fee Patents Found |
|-------|-------------------|
| Kimi K2.5 | 268 |
| Claude Sonnet | 169 |

Kimi found 59% more fee patents than Claude on the same document. This was the first evidence that model quality isn't a single axis — different models have different strengths on different document types. Kimi excels on tabular/repetitive allotment records; Claude excels on narrative testimony and correspondence.

**But performance varied dramatically by document type:**
- Doc 695 (BIA administrative records): 99% of Claude
- Doc 798 (legislative correspondence): 70% of Claude
- Doc 811 (multi-decade litigation): 66% of Claude

**Lesson:** "Which model is better?" is the wrong question. The right question is "better at what, on which kind of document?"

## Phase 4: The HPC Infrastructure Failures (March 26–April)

### The SLURM partition routing problem

UVA HPC has A100 80GB GPUs, but the SLURM partition `gpu-a100-80gb` had zero nodes assigned. Jobs submitted to that partition queued indefinitely — not failing, just waiting. The A100s existed on the general `gpu` partition, but the specific routing constraint sent jobs to an empty queue. This wasn't diagnosed for days, during which we assumed our jobs were just in a long queue.

### The salloc-vs-sbatch mistake

The AI assistant (Claude Code) set up HPC extractions to run through interactive SSH sessions — meaning the extraction depended on my laptop staying open, connected to the university network, and awake. Close the laptop, lose WiFi, or let the screen sleep, and the job dies mid-extraction with no saved results. This happened more than once before we caught the pattern.

The fix was obvious in hindsight: submit the work as a `sbatch` job — a batch submission that runs independently on HPC, writes output to persistent files, and doesn't care whether your laptop is on or off. That's the entire point of a batch scheduler. But Claude Code defaulted to the interactive approach because it could see the output in real time, which made debugging easier for *it*. The convenience of the AI assistant drove an infrastructure choice that was wrong for the researcher.

**Lesson:** When an AI assistant sets up infrastructure, its incentives aren't aligned with yours. It prefers interactive sessions because it can see what's happening. You need batch jobs because you have a life outside the terminal. Check how things are wired, not just whether they work.

### The Qwen OOM cascade

Getting Qwen 2.5 72B running on HPC required four failed attempts in sequence:
1. First try: OOM at 128GB RAM during model loading. Bumped to 256GB.
2. Second try: max_model_len too high for GPU memory. Reduced from default to 16K.
3. Third try: model name mismatch — vLLM serves models under a different name than the HuggingFace model ID. The extraction script was requesting a model that didn't exist on the server.
4. Fourth try: finally ran — and produced garbage output.

Each iteration required resubmitting a SLURM job, waiting for allocation, waiting for model loading (~15 min), running the test, and discovering the next problem. A full day of HPC time for a model that turned out to be unusable.

## Phase 5: The RC GenAI Debugging Saga (April 2–9)

**Goal:** Use UVA Research Computing's new GenAI service (Kimi K2.5 on 8x H200 GPUs) as a free, university-owned extraction backend.

**What happened:** 99% failure rate on production-length prompts.

For days, we assumed the problem was nginx proxy timeouts on RC's side. We filed support requests. We tested shorter prompts (which worked), leading us to believe there was a content-length limit. We wrote retry logic. We reduced chunk sizes.

**The actual problem:** RC GenAI had switched from returning standard JSON responses to Server-Sent Events (SSE) streaming format — without announcement or documentation. Our code expected:
```json
{"choices": [{"message": {"content": "..."}}]}
```
The server was sending:
```
data: {"choices": [{"delta": {"content": "..."}}]}
data: {"choices": [{"delta": {"content": "..."}}]}
data: [DONE]
```
The JSON parser choked on the first `data:` prefix, threw an exception, and the generic error handler reported it as a connection failure. We were debugging a network problem that was actually a parsing problem.

**The fix** was 40 lines of SSE parsing code. Days of debugging for 40 lines.

**Then a second surprise:** Kimi K2.5 sometimes routes its answer through a `reasoning` field instead of the `content` field. The SSE stream has both. If you only read `content`, you get an empty response ~20% of the time. You have to check both fields and take whichever one has the answer.

**Lesson:** When an API returns errors on long inputs but succeeds on short ones, the instinct is to blame content length. But format changes can also be length-dependent (short responses might fit in a single SSE chunk that happens to parse as JSON).

## Phase 6: The Stella Bug — Five Stacked Pipeline Failures (April 10)

**The symptom:** A user queried the DOJ index cards database for "tell me about taxes." The AI returned an analysis dominated by eight women all named Stella. The actual database has 6,588 persons — "Stella" appears at a normal ~0.85% frequency.

**Why this happened — five bugs stacked on top of each other:**

1. **v4 extraction types fetched but silently dropped.** The code fetched testimony, taxes, and mortgages from the database into a Python dict, then the prompt-building function only rendered entities, events, transactions, and relationships. 1,553 tax records and 634 mortgage records were retrieved on every query and then thrown away before the AI could see them.

2. **No search functions for the index card schema.** The search layer had no `search_record_slips()` or `search_legal_cases()` function. For the index cards database, keyword search could only find records indirectly through entity context fields — which is where the biased Stella cluster came from.

3. **The synthesis prompt lied about available evidence.** The prompt told the AI "YOU HAVE MULTIPLE TYPES OF EVIDENCE: entities, events, testimony, taxes, mortgages, legislative actions..." regardless of which database was being queried. For a database with empty tables, the model was told it had data it never received.

4. **When evidence was thin, the AI substituted its training data.** With only a handful of entity matches to work with, Claude Opus filled the analysis with information from its training corpus — the Burke Act, the Dawes Act, the Cato Sells competency commissions. The output read as authoritative but contained nothing from the user's actual archive.

5. **Natural language questions returned zero results.** The full-text search used strict AND matching: "trace U.S. v. Pennington County" required every word — including "trace" — to appear in a single database row. Since "trace" doesn't appear in DOJ slip data, the query returned nothing, and the pipeline fell back to the biased entity data.

**Why this matters for DH researchers:** Each bug was individually minor. The pipeline appeared to work — it produced fluent, well-structured, historically plausible text. The problem was that the text wasn't grounded in the archive. This is the fundamental risk of LLM-assisted research: the failure mode isn't an error message, it's a confident, well-written answer that happens to be wrong. The only way we caught it was because "eight women named Stella" was absurd enough to notice. A subtler version of the same bug — an analysis that draws 80% from the archive and 20% from training data — would be much harder to detect.

**The fix** required changes to five different functions across the data retrieval, prompt construction, and search layers.

## Phase 7: The Deep Read Pipeline Gap (April 13)

**The problem:** The Streamlit app's Deep Read mode sends the full document text plus extraction data to the analysis model (Claude Opus). For Survey Part 33 (~180K tokens), the text was truncated to ~150K tokens to fit the context window. This meant Opus couldn't see ~17% of the document.

**The compounding problem:** This truncation should have made the extraction data *more* important — it covers the full document via chunk-by-chunk processing. But the Deep Read mode only sent 4 of 10 extraction types to the analysis model: entities, events, transactions, and relationships. It did not send testimony (130 Sonnet items / 50 Kimi items), correspondence (106/52), legislative actions (92/43), fee patents (5/0), taxes, or mortgages. These records sat in the database, invisible to the analysis model.

**How we found it:** We set up a head-to-head comparison of Kimi and Sonnet extractions on the same document (Survey Part 33), using the same analysis model (Opus) and the same question. The idea was to test whether Sonnet's richer extraction (2,859 items vs. Kimi's 1,583) actually produces better research answers. The initial results showed Sonnet was somewhat better — but not dramatically, despite having nearly twice the data. That seemed wrong, which led us to check what data was actually reaching Opus. The answer: only the 4 original extraction types. The testimony, correspondence, and legislative actions that accounted for the bulk of Sonnet's advantage were sitting in the database, never sent to the analysis model.

**The reveal:** After fixing the code to send all 10 types, we re-ran the same query ("tell me about the 18 unratified treaties") with the *Kimi* extraction. The result was dramatically better — Opus now surfaced the Kahn bill, the enrollment rolls, the lost testimony problem, and the population decline narrative, all from Kimi's 50 testimony records and 43 legislative actions that had previously been invisible. Most of what we'd attributed to Sonnet's superior extraction was actually just Opus reading the full text more carefully with more context.

**The key finding:** The biggest improvement came not from switching extraction models but from fixing the pipeline to use data it already had. The code fix mattered more than the extraction model difference.

**The meta-lesson:** Claude Code built this pipeline and then analyzed the results of a comparison run on this pipeline. It initially presented the Sonnet-vs-Kimi gap as a model quality finding, when the real problem was in its own code. When the assistant that writes the code is also the one interpreting the results, its blind spots compound. In a traditional software project, the developer and the analyst are different people, which provides a natural check. When one AI agent fills both roles, you lose that check unless you actively provide it.

## Phase 9: Vision Extraction — Index Cards (April 6–10)

**Goal:** Extract structured data from 87 NARA RG 60 DOJ index card PDFs (scanned handwritten/typed record slips from early 20th century).

**Claude Sonnet vision:** 12,969 record slips, 4,811 legal cases, 6,588 persons. Cost: ~$130. Reliable.

**Qwen-VL 72B (HPC, 4x A100):** 13,887 slips (+7%), 9,591 cases (+99%), 3,998 persons (−39%). Free.

**Kimi K2.5 vision (RC GenAI):** Failed. 45% of pages timed out at ~51 seconds. On the pages that worked, Kimi put its analysis into the `reasoning` field as narrative description rather than producing structured JSON. Kimi's strength is text comprehension, not vision. Abandoned.

**The Sonnet vs. Qwen dedup puzzle:** Qwen found 99% more legal cases but 39% fewer persons. This looked like a quality difference until we examined the outputs: the models use different deduplication strategies. Qwen creates a separate `legal_case` entry for each *mention* of a case (an audit trail). Sonnet deduplicates cases but captures more secondary individuals (attorneys, judges, witnesses). Neither is wrong — they produce different downstream affordances. This meant the planned merge of Sonnet + Qwen extractions was complementary, not redundant.

## Phase 10: The Taylor Report — Vision Extraction on Tabular Data (April 2–3)

Extracted the AIPRC Indian Land Consolidation Report (Taylor Report, 1976) using Claude Sonnet vision. 44 batch extractions covering tables of federal land takings 1936–1974.

Key finding: 1,811,010 acres lost through government takings, with the Pick-Sloan Missouri Basin dams as the largest single dispossession (175,700 acres at Fort Berthold alone). The document contains data the federal government acknowledged it could not fully recover.

This was a straightforward success — noted here primarily because the tabular data extraction worked cleanly on the first attempt, in contrast to the extensive debugging required for the text extraction pipeline.

## Summary: What We Learned

**1. Fine-tuning doesn't transfer comprehension.** Teaching a model the output format doesn't teach it to read carefully. The gap between Claude and open-source models is in reading comprehension, not JSON formatting.

**2. "Which model is better?" is the wrong question.** Kimi found 59% more fee patents than Claude on the same document. Claude found 80% more testimony items than Kimi. Model quality depends on document type, and the optimal pipeline uses different models for different tasks.

**3. The pipeline matters as much as the model.** The Deep Read truncation bug meant that switching from Kimi to Sonnet extraction showed almost no improvement — because the pipeline was throwing away Sonnet's extra data before the analysis model could see it. Fixing the pipeline with the *same* extraction data produced a bigger improvement than switching models.

**4. LLM failure modes are silent.** The Stella bug produced fluent, well-structured, historically plausible text that was wrong. The pipeline didn't crash; it confidently presented training-data-derived claims as archival findings. In a research context, this is more dangerous than an error message.

**5. Infrastructure debugging dominates researcher time.** The RC GenAI SSE format change, the SLURM partition routing, the Qwen OOM cascade — these consumed more hours than any analytical question. DH projects using LLMs should budget infrastructure time at 3–5x the analytical work.

**6. AI assistants can introduce errors into their own analysis.** When Claude Code built the pipeline and then analyzed the pipeline's output, it made incorrect claims about its own code (the schema confusion). The assistant's statements about what the code does must be verified against what the code actually does.
